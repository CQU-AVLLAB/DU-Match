# Cityscapes 训练排错与服务器预检（2026-10-16）

## 已确认的情况

同一台 RTX 4090 Laptop 16GB，同一个 Cityscapes 1/16 划分，DINOv2-Base，798×798，batch 1：

- 原始 FP32 路径：专用显存约 15.14GiB、共享系统内存约 12.79GiB，观察至少 85 秒第一步仍未完成，手动停止。
- 只启用 BF16：进程异常退出，没有保留 traceback，不能据此断言具体退出原因。
- 原生 SDPA + BF16：两次独立短测均完成 40 步，包括 30 步启用 DUE/CEM/UCCL 的阶段。第一次平均 0.376 秒/步，显存分配峰值 10.866GiB；第二次由预检脚本完成，见 preflight.json。

## 主要瓶颈

当前环境没有 xFormers。原始 DINOv2 的注意力回退路径显式计算并保存注意力矩阵。
518 裁剪有 37×37 个 patch，798 裁剪有 57×57 个 patch；包括 CLS token，单头矩阵面积之比约为 (3250/1370)^2 = 5.63。
高分辨率下，该实现产生大量中间张量。Windows/WSL 可能借用共享系统内存，因此未必立即报 CUDA OOM，而是先极度变慢。

证据支持这是原始运行的主要显存瓶颈；此前 BF16 异常退出的精确原因仍未确定，不能把所有失败都归于它。
原生 SDPA 与 BF16 同时启用后的成功，也不能单独量化二者各自的贡献。

## 改动及检查

- `--torch-sdpa`：显式选择 PyTorch 原生注意力，避免依赖额外安装 xFormers。
- `--amp-bf16`：前向使用 BF16，概率计算、原型统计和损失计算保留 FP32。
- 两个选项默认关闭，原始训练路径保留。
- 新旧注意力输出、输入梯度和参数梯度的小张量数值对照通过。
- 原始基线默认输出及互补扰动仍逐位一致；7 个 DU-Match 公式/梯度/状态测试全部通过。
- 基线和 DU-Match 的正式公平比较必须使用一致的精度与注意力实现。

## 租服务器后先运行预检

上传 DU-Match 代码、DINOv2-Base 预训练参数和 Cityscapes 数据后，在仓库根目录运行：

```bash
python scripts/preflight_cityscapes.py   --data-root /实际路径/cityscapes   --batch-size 1   --output exp/preflight_cityscapes_server_01
```

脚本先检查 CUDA、BF16 支持、所有划分列出的数据文件、训练/验证交叉、首张训练掩码的 trainIds 编码和预训练权重，再运行 40 步真实训练。
预检配置仅将原型预热缩短为 10 步；不会改正式配置的 1000 步预热。
日志持久保存在输出目录，不再放 `/tmp`。单独保存退出码、环境、完整命令、每步耗时、损失和显存记录。
预检限制 PyTorch 分配器最多使用 85% 可见显存，避免再次长时间借用共享内存；上限不能约束驱动和其他程序的显存。
不支持 BF16 的服务器会用 FP32 + SDPA 测试，是否能跑需以该次结果为准。
任何检查失败则停止，不自动开启长训练。每次使用新输出目录。

如果计划正式使用 batch 2，应再用 `--batch-size 2` 检查，而不是把 batch 1 结果当作 batch 2 的保证。
当前本机通过的是 batch 1；该设置的反向 batch CutMix donor 为自身。

## 仍需在正式训练前完成

40 步短测证明训练路径与短时资源需求，不证明训练效果或长期稳定性。
正式跑分前还应检查保存/恢复检查点、官方 798 滑窗验证、长一点的稳定性及最终对照设置。
目前没有正式验证耗时。约 0.34–0.38 秒/步意味着 502020 步纯训练约 48–53 小时，不包含验证与保存。
